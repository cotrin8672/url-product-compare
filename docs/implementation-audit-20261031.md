# 実装・本番接続の不足調査

確認日: 2026-10-31。対象は商品比較・ふるさと納税・証券会社比較、楽天／ValueCommerce／アクセストレード、本番のPages・Lambda・通常設定。過去要望のAmazon／Yahooについても、実装済みSDKと未接続の比較機能を区別した。認証情報の値は記録していない。

## 先に直すもの

1. **ふるさと納税の「検索→選択→比較」が422で失敗する問題。** 設定不足とは別に、本番で再現した。
2. **楽天APIのクレジット表示。** 広告表記は存在するが、楽天の指定する提供元クレジットがない。
3. **さとふるの本番設定と横断比較の実証。** トークンだけでなく通常設定のサイトID・広告スペースIDも未設定。
4. **証券の条件更新と広告接続。** 3社すべて試算停止中で、広告リンクも未設定。

P0は現在の機能不成立・公開時の要対応、P1は主要機能や安定運用の不足、P2は運用・対象拡張。設定待ちをコード未実装として数えない。

## 実装上の不足

| ID  | 優先         | 不足・影響                                                     | 根拠と必要な対応                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| --- | ------------ | -------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A01 | P0           | **楽天の返礼品再取得が不安定。検索できた商品が比較できない。** | [lookup](../packages/backend/src/providers/rakuten/http.ts)はURL末尾から検索し直し、最大3ページで照合する。非数値slugの2件で失敗。[画面](../apps/furusato/src/FurusatoApp.tsx)は検索結果のAPI商品IDを比較参照へ渡していない。API商品ID＋正規URLで再取得・照合する参照形式と、実例の回帰テストが必要。クライアントの商品情報をそのまま信頼する修正にはしない。                                                                                                                                               |
| A02 | P0           | **楽天APIのクレジット表示がない。**                            | webソースに指定のクレジットリンク・バナーがない。「広告」表示とは別。[公式ガイド](https://webservice.rakuten.co.jp/guide/credit)はAPI利用時のクレジットを要求している。指定HTMLによる表示が必要。                                                                                                                                                                                                                                                                                                           |
| A03 | P1           | **商品比較は楽天内だけ。三店横断比較は未接続。**               | [bootstrap](../packages/backend/src/bootstrap.ts)がConsumerProviderへ登録するのは楽天だけ。[consumer-service](../packages/backend/src/comparison/consumer-service.ts)の候補探索も入力元の1プロバイダーだけを検索する。Amazon／Yahooの検索・詳細・成果リンクSDKは存在するが、比較用アダプター、サイト横断の候補探索・同一製品/バリエーション照合・表示統合は別途必要。Amazonの`ai:false`・`priceComparison:false`を無条件に解除して接続しない。現在の3サービスのSecretに追加のキーを要求する話とは区別する。 |
| A04 | P1・対象確認 | **アクセストレードはWSIDの保存・検証と診断だけ。**             | [lambda-bootstrap](../packages/backend/src/lambda-bootstrap.ts)はWSIDを読み取るが、本番APIの処理に渡していない。`packages/*`にAT用SDKはなく、[診断](../tooling/check-accesstrade.mjs)だけが商品Webサービスを呼ぶ。証券の承認済み広告を手動登録する経路は別に実装済み。WSIDを設定してもNISA案件が自動表示される状態ではない。商品APIが証券案件を扱えるとは確認できておらず、自動取得が必要なら対象API・案件の確認から行う。静的比較＋手動広告を選ぶ場合はATの商品SDKを公開の必須条件にしない。               |
| A05 | P1           | **証券条件の更新経路がないため全試算が停止。**                 | [catalog](../packages/backend/src/providers/securities/catalog.ts)は10/25確認・10/26次回確認の固定値。[比較処理](../packages/backend/src/comparison/securities.ts)が期限後を保留する一方、ページアクセス時の公式情報取得→Jev変更判定→検証・保存が未実装。定期実行を追加せず、合意したアクセス時更新か手動更新の再現可能な手順が必要。広告側にも必須の`approvedUntil`が残るため、実際の掲載期限と運営独自の停止日を混同しない設計整理が必要。                                                                |
| A06 | P1           | **選択式返礼品を採点可能な候補へ絞る処理がない。**             | 今回の検索上位6件は単位寄付額を算出できず、追試2件は寄付額に価格幅があり内容量がconflict。[抽出](../packages/backend/src/comparison/furusato.ts)が曖昧な量を捏造しないこと自体は正しい。単一仕様の候補選別、選択式・定期便の扱い、取得可能な範囲でのバリエーション指定が不足。APIにないSKU情報をAIで埋めない。6件の結果を全返礼品の抽出失敗率とは解釈しない。                                                                                                                                               |
| A07 | P2           | **返礼品の比較・採点対象が狭い。**                             | [furusato](../packages/backend/src/comparison/furusato.ts)のカテゴリは米・肉・果物・魚介。[採点](../packages/backend/src/comparison/furusato-scoring.ts)はkg当たり寄付額・総重量・配送形式の確定を必須にする。個数/尾数/容量で比べる品や日用品・家電・体験には汎用対応していない。対象カテゴリ別の数量単位・比較軸・採点前提の拡張が必要になる。初期4カテゴリ以外は対象拡張として扱う。                                                                                                                     |
| A08 | P1           | **ふるさと比較にサーバー側の取消・再送重複排除がない。**       | [画面](../apps/furusato/src/FurusatoApp.tsx)の「中止」はブラウザーのAbortだけ。[比較API](../packages/backend/src/comparison/commerce.ts)は同期処理で、渡されるのは内部の25秒タイムアウト。商品比較にあるジョブID・冪等性キー・サーバー側取消はつながっていない。再送時の重複採点、離脱後の処理継続、再読込時の復元を扱う必要がある。既に始まったAI呼び出しの料金を取消で取り消せるとは限らない。                                                                                                            |
| A09 | P1           | **楽天のAPI呼び出し頻度がLambda全体で共有されない。**          | [楽天SDK](../packages/rakuten-api/src/index.ts)の1.1秒キューはクライアント／プロセス内のみ。API・worker・複数インスタンスで共有されない。HTTP受付のDynamoDB制限はあるが、1ジョブ内の複数の上流呼び出しまでは数えない。並列時の共通調整と429時の扱いの検証が必要。今回の単一ジョブ成功を並列負荷の保証にしない。                                                                                                                                                                                             |
| A10 | P1           | **障害通知・有料AI消費量の運用が不足。**                       | [テンプレート](../infrastructure/lambda/template.json)と実AWSで確認できたアラームはCleanup Errorsのみで、通知先0件。API／worker失敗、タイムアウト、Jev失敗・有料呼び出し総数を継続監視・通知する実装は確認できない。リクエスト件数制限と呼び出し数の上限はあるが、実課金額の上限ではない。上流の`lookup_incomplete`を一般的な`invalid_response`へ潰すため切り分けも難しい。秘密値を出さない段階別の診断・通知が必要。                                                                                       |
| A11 | P2           | **運営・問い合わせ・プライバシー情報の公開ページがない。**     | 上記3URLは本番404で、対応するページ実装・案内リンクも確認できない。審査・利用者対応のため、運営情報と実際のデータ取扱いに合わせたページを整備する。広告表示は既にあり、「広告表記が一切ない」という指摘にはしない。                                                                                                                                                                                                                                                                                         |
| A12 | P2           | **設定投入・デプロイ確認の手順と文書が揃っていない。**         | Secretと通常設定の分離、ローカルの[形式チェック](../tooling/check-lambda-configuration.mjs)は実装済み。ただしSecret保存後のLambda再反映、通常設定との照合、実API疎通までを一度に行う常設ツール／CIはない。GitHub Actionsはverifyのみ。不正な任意プロバイダー設定がbootstrap全体を止めるため、投入前の検証と失敗時の復旧手順が必要。証券文書のSecret内広告設定、旧仕様書のFirestore・メモリ制限など、本番と異なる説明も残る。歴史的な試験記録は消さず、現行の入口文書を整理する。                            |

## 不足と混同しないもの

- 楽天・ValueCommerce・Jevの再利用SDK、商品比較の非同期ジョブ・復元・冪等性・期限、返礼品のカテゴリ別項目と画像・総合スコア用処理、証券の静的比較と広告表示の枠は存在する。
- ふるさとの比較点は返礼品全体に1つ。品種等の属性を個別採点したり、日本語の理由文を生成する追加実装は要求に含めない。
- 不明・矛盾・異なる仕様の価格を無理に順位付けしないこと、Amazonの利用制限、API結果の鮮度管理は意図した制限であり、点数を表示するために解除しない。
- 証券の初期対象は3社の代表カード・国内現物。dカード/JCB/Olive等や米国株などの網羅性は別の対象拡張であり、今回のAPIトークン設定の不足ではない。
- 定期実行を使った証券条件更新は提案しない。既存のジョブ後始末用Cleanupが定期実行されていることとは分けて扱う。

この文書は不足の洗い出しで、機能コードの修正や新しい外部サービスの登録は行っていない。
