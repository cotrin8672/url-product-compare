# Jev判定の改善方針 — 2026-10-02

これは現行コード・保存した実API応答を調べて策定した改善案である。策定時点では新たな課金API呼び出し、モデル変更、既存正解の変更を行っていない。その後、利用者の実装指示により共有判定と呼び出し元を変更した。[実装と実API検証の結果](jev-prepared-report.md)に、修正した範囲と未完了部分を記録する。以下の「現在」は策定時点の状態。

## 1. 改善する対象

要件書§4.4の「製品同定・候補探索・数値処理・必須条件はコード、残った製品の条件適合と推薦判断はJev」という分担を維持する。Jevを外してルール式の推薦を完成扱いにしない。

現在の画面では登録済み充電器の離散的な希望照合をコードで行っており、旧Jevデモと評価CLIは診断用。水筒の実URL比較は未対応。以下は、この未完成の取得・比較フローへ接続するための判定設計である。

添付仕様書のカテゴリ別比較定義・未登録カテゴリの未対応扱いは維持する。任意の未知カテゴリについてAIが軸を生成すれば実比較できる、という保証はしない。現在の4型番限定は要件の完成条件ではなく、実装上の不足である。

## 3. 最優先: 信頼度に棄権を代行させない

現在の水筒質問には「不明・対象外ならconfidenceを0.7未満にする」という指示がある。しかしconfidenceは回答分布から計算される値で、データ取得の確認状態を返すフィールドではない。この指示を止める。高いconfidenceでも事実確認済み、根拠十分、希望適合であることを保証しない。

採点前の分岐を明示する。

| 状態                                           | 処理                                       |
| ---------------------------------------------- | ------------------------------------------ |
| 利用者に不要な軸                               | 全候補の質問から除外                       |
| 希望の意味が複数あり、評価が変わる             | 解釈候補を確認。未確定のまま採点しない     |
| 必須条件への不適合が確認済み                   | 候補を除外。別の加点で相殺しない           |
| 必須条件や有効な希望軸に必要な根拠が不足・矛盾 | 候補の総合順位を保留。欠損を低得点にしない |
| 根拠・条件が揃う                               | 限定した意味判断をJevへ送る                |

現行rankProductsは欠損キーを止めるが、文字列が「Not verified」でもキーが存在すれば事実扱いできる。単なる禁止語リストで直さず、取得側で確認状態と事実値を分け、有効な値だけを候補へ渡す。

## 4. 要件・根拠・評価軸をつなぐ

### 利用者の条件

自由文をそのまま採点に渡す前に、必須/希望/不要、対象の操作・場面、許容する制約、重要度へ分ける。原文との対応を保持し、AIの抽出案で意味が確定しない場合は確認する。「ねじらず開けたい」からボタン操作・片手操作・軽い操作力まで勝手に確定しない。

URLだけの入力に、利用者が言っていない希望を付け足さない。標準の用途を使う場合は、その用途・評価基準を表示し、個人の希望への適合と区別する。

### 判断を裏付ける根拠

事実ごとに対象型番・バリエーション、取得元、該当記述、取得時刻、単位・試験条件を保持する。提供元の事実と、抽出した値と、コードで計算した適合状態を区別する。複数資料が矛盾する場合は都合のよい記述を選ばない。

出典URLの添付だけでは判断の裏付けにならない。例えば説明書の開閉手順は「フタを回して外す必要があるか」を支えられるが、操作力や片手での開けやすさを保証しない。比較軸ごとに、必要な証拠と禁止する推論を明記する。構造検証だけで根拠の意味的な十分性を保証できるとは扱わず、その対応自体を資料付き事例で検証する。

Jevには質問に必要な、確認済みの短い記述・条件・コード判定を送る。原資料と抜粋の対応はサーバー側で保持し、必要な抜粋を送る場合はAI利用権限も確認する。JevにURLを渡して再調査させたり、全文を送れば精度が上がると考えたりしない。

### 評価軸の採用

カテゴリの比較定義から、確認済みの用途・希望に関係する軸を選ぶ。軸は候補の得意分野や取得できた項目を見てから都合よく変更しない。全候補に同じ尺度・重みを使い、有効軸の欠損を理由に候補ごとの重みを再正規化しない。同じ特徴を複数軸で二重加点しない。

新しい軸には、用途との関係、必要な根拠、各水準、境界・反例、保留条件、検証記録が必要。動的に作った軸はその場で品質が確認されたことにはならない。

## 5. 質問型と評価尺度を作り直す

開閉方式や折り畳み形状など、確認済み離散値の照合はコードで処理する。これをScoreで再分類しても、比較判断の精度を高める証拠にはならない。

Jevは、資料に明記された操作上の制約が、確認済みの利用場面・希望にどう対応するかなどの意味判断を担当する。ただし資料にない利便性や品質は推測させない。全体を一問の「どれがおすすめか」にまとめず、一つの希望・制約につき一観点を評価し、検証した重みで集約する。

| 判断の性質                         | 方針                                                                               |
| ---------------------------------- | ---------------------------------------------------------------------------------- |
| 数値・既知の真偽・既知の方式の照合 | コード。Jevで再採点しない                                                          |
| 意味上の二択                       | Noulを評価候補にする。不明を否定へ混ぜないよう、根拠充足を別に確認                 |
| 順序のない意味分類                 | Choiceを評価候補にする。必要なら「記載なし」「曖昧」「矛盾」を明示した選択肢にする |
| 区別できる段階のある希望適合       | Score。一質問一観点、各水準は単独で理解できる具体的な状態                          |

現行Judge/adapterはScore専用。Choice/Noulへの変更は改善実験で効果を測ってから必要な範囲を追加する。型を変えるだけで精度が上がるとは扱わない。不明をScoreの最下段や中間段へ追加すると「不明」と適合の大小を混ぜるため採用しない。

水準は「高機能だから高評価」ではなく「確認済みの希望を満たすか」に合わせる。部分適合の意味を説明できない二択に、形式的な中間水準を作らない。各水準に参照対象を明記し、質問と水準が別の判断を要求しないようにする。

質問IDはモデルへ意味を伝える代わりにはならない。instructionsと水準本文に観点を記載する。日本語を英語へ変換する案は、希望・否定・対象範囲の保存を含めて比較検証する。翻訳だけで品質が改善したとは判断しない。

## 6. 集約・同順位・出力の扱い

confidenceを適合スコアへ掛けたり、購買満足率・事実の正しさへ読み替えたりしない。現在のprobabilities/legend/scoreの形式検証は維持し、同じ平均でも分布が異なるケースを確認する。

重要度はユーザーの確認した条件と評価定義から先に固定する。必須条件は集約の外で検査する。小差を単純に順位差へ変えず、実測した揺れと独立事例で同順位の幅を決める。全体共通の0.7だけで公開可否を決めない。

理由は採用した事実・コード判定・評価軸への参照から構成し、Jevに説明文や出典を創作させない。比較不能・モデル不確実・一時障害を別状態にする。Jev障害時に暗黙にルール式の推薦へ切り替えない。表示指数を100倍しただけで校正済み適合度％にはしない。

## 7. 改善を判定する実験

既存の固定原票・正解・実応答は保存する。既知の失敗は開発用の回帰事例として使い、その事例での改善を独立精度と数えない。

1. 採点前ゲートを確認する。不要軸・不足事実・未確定条件に対して、実際に質問/呼び出しが発生しないことを調べる。拒否した件数をモデル精度へ足さない。
2. 新しい資料付き実製品・利用条件に、モデル応答を見る前に私が根拠と期待判断を付ける。資料だけで正解が決まらない事例は推測で正解ラベルを付けない。同一担当の評価であることは明記する。
3. 同じ製品で希望を逆転、不要軸を追加/削除、事実の表現を変更した対照例を作る。原資料上の事実、ユーザーの意味、コード判定、Jevの判断を別々に検査する。
4. 軸ごとの最小state、現行の共有state、具体化した尺度、必要な質問型を一変更ずつ比較する。回答率、誤り率、遅延、呼び出し数を併記し、追加呼び出しの効果を測る。
5. 調整に使わない製品・型番系列・資料を分け、質問・重み・閾値を固定して検証する。反復は揺れの測定であり独立製品に数えない。正しい回答だけを選び直さない。
6. 実URLから、同定・候補探索・根拠取得・必須条件・Jev評価・根拠付き表示まで通す。手入力の仕様だけが通ることをサービスの推薦品質に読み替えない。

測るのは、根拠のない採点、高信頼の誤り、必須条件違反の推薦、首位の許容性、同順位・希望変更への追従、保留率と判定カバレッジ。全部保留にして一致率を上げる方法は採用しない。公開目標と対象範囲は検証前に固定し、順位と％は別に評価する。

## 8. 実装の優先順

1. 取得状態と確認済み条件を共有判定へ接続し、欠損・不要・曖昧を採点前に処理する。
2. 問いと尺度を希望適合へ統一し、根拠が支える範囲を定義する。現在の単純な方式照合を主なJev品質試験から外す。
3. 軸ごとの入力範囲と質問型を、資料付き事例で比較する。新しい依存や複数AIの常時投票は追加しない。
4. 実取得経路へ接続し、未使用の製品・系列で一連の比較品質を判定する。公開順位/％を有効にする判断は、この結果まで行わない。

## 9. 確認した公式資料

- [Jev 1.13の既知の限界](https://docs.typesafe.ai/model-jaggedness/jev-1.13): 数値処理、間接的な質問、不要なstate、矛盾する質問・基準の制約。
- [Score](https://docs.typesafe.ai/primitives/score): 一観点、具体的な水準、各水準は単独で評価されること、scoreと分布の関係。
- [Confidence](https://docs.typesafe.ai/confidence): confidenceは回答分布から計算され、確認済み事実の状態を表す値ではない。
- [Noul](https://docs.typesafe.ai/primitives/noul)、[Choice](https://docs.typesafe.ai/primitives/choice): 二択と順序のない分類の質問型。現行コードでの対応は未実装。
