# 家電・PC比較のAPIと処理フロー

更新: 2026-10-13。

## 公開画面とゲートウェイ

Webの操作は商品URLの送信です。カテゴリを自動判定し、複数候補の場合だけ選択します。条件入力・トークン入力・取消操作・出典展開はありません。ネットワーク処理はAPIクライアントを使います。

公開ゲートウェイは次の経路だけを内部APIへ接続し、サーバー側のBearerトークンを付与します。トークンをHTML・JavaScript・URL・利用者入力に含めません。detectと開始のPOSTはクライアントIPごとに1分6回、インスタンス単位で制限します。

| 公開経路                   | 用途                                                           |
| -------------------------- | -------------------------------------------------------------- |
| `GET /api/catalog`         | 公開カテゴリ・評価軸・プロバイダ定義                           |
| `POST /api/detect`         | 商品URLのカテゴリ候補を取得                                    |
| `POST /api/comparisons`    | 操作IDと `x-comparison-key` で開始。新規202・同じ操作の再送200 |
| `GET /api/comparisons/:id` | `x-comparison-key` で進捗・結果を取得                          |

ゲートウェイは接続元アドレスと許可Originをサーバー情報から検証します。制限用のIP記録は最大1024件で、満杯なら新しい記録を受け付けません。取消・同期比較・既存診断を公開しません。

画面の開始入力に `idempotencyKey` を追加して送信します。

```json
{
  "url": "https://item.rakuten.co.jp/shop/product/",
  "category": "laptop",
  "conditions": {},
  "sort": "recommendation",
  "keyword": null
}
```

`category` は検出したカタログIDです。`null` でサーバーの自動判定も使えます。`sort` は公開URLの `price / recommendation / specifications` に従い、通常は `recommendation` です。画面の `conditions` は空です。内部APIの条件スキーマと同期比較は保持します。

開始前に操作ごとのランダムなIDとアクセスキーを作り、通信再送では同じ組を使います。異なる入力で同じ操作IDを使うと409、異なるキーは403です。サーバーはキーのハッシュを保持します。sessionStorageにはジョブID・キー・期限・revisionとカテゴリIDだけを保存し、商品情報やBearerトークンは保存しません。

## 内部処理と結果

1. 入力URLに対応するプロバイダと取得・表示・成果リンク権限を検証する。
2. URL完全一致の掲載を取得し、ジャンルと祖先、型番・JAN、広告リンクを照合する。全カテゴリで新品の根拠が必要。自動カテゴリは楽天の属性名をJev Noulで主要項目に絞り、ジャンルごとにキャッシュする。
3. カテゴリ語とジャンルで30掲載ずつ最大3ページ検索し、新品と確認できる各ページ最大6掲載を比較処理へ渡す。新品がないページでも後続ページを探索する。比較処理は最大18候補に限定し、掲載ID・URL・確認済みJANの重複を整理する。ふるさと納税の掲載は通常販売品と分ける。
4. 明示された仕様と引用を抽出する。判断が必要な値は任意のJev Choiceへ送る。既存6カテゴリは最大24問・1回、自動カテゴリは6商品の最大96問を16問ずつ最大6回。商品名・本文から取り出した値以外を生成させず、矛盾・失敗・低確信は未確認のままにする。
5. 入力商品と最大5候補を選び、自動カテゴリの確認済み属性をJev Scoreで1回まとめて採点する。同じ項目・値は1問を共有する。権限と期限を再確認して100点スコア・共通項目の総合・成立する順位を返す。

追加探索は35秒を目安に打ち切り、AI処理には追加10秒の開始期限を設けます。楽天取得・Jevは8秒、ジャンルは5秒のタイムアウトと取消信号を組み合わせます。探索上限や取得エラーは市場全体の探索完了を意味しません。`aiCalls.openai` は0、`aiCalls.jev` は実際の呼び出し回数です。既存6カテゴリは最大1回、自動カテゴリは選定1回・抽出最大6回・採点1回の最大8回で、選定キャッシュを使えば最大7回です。

ジョブ状態は `queued / running / succeeded / failed / cancelled`。応答は単調増加する `revision`、処理段階、探索数、期限を持ちます。成功値は `category / categoryDefinition / providerDefinitions / conditions / sort / source / products / status / aiCalls / extractionStatus / search / storageExpiresAt` です。自動カテゴリは `categorySelectionStatus` と、総合に使った軸IDの `scoreBasis` も返します。

商品には価格幅、税・送料・在庫、商品URL・広告リンク、画像、同定状態、任意のJAN、取得・期限日時を持たせます。`consumerInformation` の `specs / facts / conflicts` に確認値・引用・出典・矛盾を保持します。画面から出典欄を除いても、APIクライアントの外部応答検証は維持します。

`axes` は定義した軸の0〜100点またはnull、`recommendationPercent` は共通項目の重み付き平均またはnullです。数値軸は小さい方を優先する場合 `最小値 / 商品の値 × 100`、大きい方を優先する場合 `商品の値 / 最大値 × 100` を丸めます。自動カテゴリの `method: "jev"` の軸は、確認済み属性値への5段階の期待値を25倍して丸め、モデル・期待値・信頼度を `assessment` に保持します。APIクライアントも値の出典、評価、換算結果、共通項目と総合を検証します。

自動カテゴリは入力商品で採点できる仕様を優先し、その項目の採点済み商品数が最大になる組を選びます。その組全体で確認できる共通軸を `scoreBasis` に記録し、画面に項目名と商品数を表示します。対象外の商品は総合点を保留し、全適合商品の総合点が揃うまで全体順位を付けません。画面は価格を円、総合と項目別評価を100点、欠損を「—」で表示し、抽出した生値も表示します。既存6カテゴリのCPU型番などの文字項目は採点しません。

## 保護されたAPIと保存

内部の `POST /api/comparisons/:id/cancel` と `POST /api/compare`、既存の診断APIはBearer認証を維持し、公開ゲートウェイから呼べません。取消にはジョブのアクセスキーも必要です。取消と完了は先に確定した終端状態を上書きしません。

開始は同じ操作IDのドキュメントを原子的に作成します。取得・進捗・完了は所有者とrevisionで制御し、Firestore作成トリガーは完了まで待ちます。再試行時は所有期限切れの処理を引き継ぎ、終端ジョブを再実行しません。

ローカルはメモリ、永続保存はプロバイダの明示許諾が必要です。未設定なら `result_storage_denied` で開始を拒否します。結果の期限は最大15分と掲載・許諾期限の最小値、メタデータは最大60分です。APIは期限切れで410を返し、画面は表と商品リンクを除きます。FirestoreのTimestamp型 `cleanupAt` をTTLに使います。
