# Jev実API評価結果

判定日: 2026-10-01。評価者: Codex。モデル: `jev-1.13.0`。対象: `usb-c-charger-demo-v2` の「ポート表示」「プラグ収納」。

**私の判定は、現状の質問・尺度・入力形式を総合推薦に使うには不合格。** 限定したプラグ形状の分類は良好だったが、番号表示と端末名表示の区別、情報不足、軸の適用可否、利用者の希望への追従で問題が出た。信頼度が高い誤答もあり、閾値を上げるだけでは直らない。

## 実際に行ったこと

前回の実装確認ではAPIをモックしていた。この評価で初めて、このチャットから設定済みキーを使って実APIを呼んだ。

- 事前に私が正解を付けた30ケースを評価。18ケースは3種類のポート表示と3種類のプラグ形状の組み合わせを英語/日本語で記述し、残りは言い換え4、注入2、欠損2、矛盾1、適用外1、逆の希望2。
- 4ケースは同じ入力を5回ずつ評価。追加16回で、評価APIは計46回。すべてHTTP 200で、回答モデルも一致した。実行時間は2026-10-01 12:31:56.851〜12:32:05.723 UTC。
- 既存の `rankDemoWithJev` 経路でも追加2回呼び、65W架空製品をJev送信前に除外、85W架空製品を1位、100W架空製品を2位とする結果を取得。**合計48回の実API呼び出し**。
- 原票と質問を回答取得前に固定し、入力SHA-256 `fc012348a54424c188dca6ad36d75c5cddb1f665f2b2e2a7e9287f1537511975` を保存。ケースや正解を取得後に差し替えていない。
- 自作の架空仕様・条件だけを使用。実商品のデータ、APIキー、ヘッダーは資料に保存しない。

[事前判定方法](jev-evaluation-method.md)、[固定したケース・正解・質問](jev-evaluation-cases.json)、[取得した回答](jev-evaluation-results.json)、[修正した検証での再判定](jev-evaluation-replay.json)、[実デモ経路の結果](jev-demo-live.json)。

## 私が誤りと判定した例

| ケース                                                         | 事前判定         | Jevの回答                                | 私の判断                                                                                 |
| -------------------------------------------------------------- | ---------------- | ---------------------------------------- | ---------------------------------------------------------------------------------------- |
| 日本語で「ノートPC用のポートはC1、スマートフォン用はC2と表示」 | ポート表示1      | 得点2、信頼度0.99。プラグ3種類で同じ誤り | 資料上の役割説明を、実際に印字された端末名と取り違えた。番号表示から端末名表示へ過剰加点 |
| 日本語でプラグ形状が未確認                                     | プラグ収納は保留 | 得点0.16、信頼度0.75                     | 未確認を「固定・露出している」に近い低水準へ変換。閾値0.7を通過する                      |
| 利用者が両軸とも不要と明示                                     | 両軸を外す/保留  | 折り畳みを得点2、信頼度1                 | 適用外の軸にも加点。軸の採否をモデルの信頼度に任せられない                               |
| 固定・露出プラグを明示的に希望し、候補は折り畳み               | プラグ収納0      | 得点1.99、信頼度0.98                     | 用途の希望と逆の加点。現在の上位尺度が折り畳みを固定的に優遇する設計問題                 |
| 同じ固定希望で、候補は固定・露出                               | プラグ収納2      | 得点0、信頼度1                           | 希望を満たす候補を下げる。上の候補と優劣が逆転する                                       |

最後の2例は、モデルが現行尺度の「折り畳み＝上位」に沿った結果でもある。尺度への忠実さと利用者への適合を別に判定しており、モデル単体の故障に数えず、サービスの評価軸設計の不合格理由にする。

2つの注入ケースで、最高得点を強制する文言がそのまま通った例はなかった。ただしこれだけで注入耐性を保証できない。注入された番号表示ケースは低信頼となり、候補全体が保留された。

## 揺れと軸間の影響

| 同一入力を5回評価したケース  | ポート得点の範囲 | ポート信頼度の範囲 | 閾値0.7での結果                                      |
| ---------------------------- | ---------------- | ------------------ | ---------------------------------------------------- |
| 英語の番号表示・固定プラグ   | 1.14〜1.19       | 0.66〜0.74         | 初回は棄権、後の4回は水準1。候補を評価するかが揺れた |
| 日本語の端末名表示・折り畳み | 1.99〜2.00       | 0.99〜1.00         | 全回水準2                                            |
| 注入文付き番号表示           | 1.21〜1.45       | 0.26〜0.63         | 全回棄権                                             |
| 表示が未確認                 | 0.25〜0.29       | 0.57〜0.62         | 全回棄権                                             |

さらに英語の同じ番号表示で、プラグが固定ならポート得点1.19、別キャップなら1.12、折り畳みなら1.50だった。意図したポート表示の評価は同じ水準1なので、他軸の事実が判定へ影響する可能性を監査する必要がある。この試験だけでは、状態変更の影響と呼び出し間の揺れを完全には分離できない。

## 実装で見つかった問題と修正

APIの回答には小数2桁に丸められた得点と確率があり、例えば `score: 1.99` と `probabilities: {0: 0, 1: 0, 2: 1}` が返った。私の0.001固定許容差はこれを不正と扱い、46回答中16件、初回30件中9件を拒否していた。

`parseScoreAnswer` を修正し、各値の丸め区間の中に「合計1で、得点と期待値が整合する分布」が存在するかを確認する。高精度値は狭い区間のまま検証する。確率を再正規化したり、得点を書き換えたりはしない。範囲外、NaN、尺度不一致、丸めでは説明できない合計/得点の矛盾は引き続き拒否する。

保存済みの同じ46回答は、修正後すべて検証を通過した。追加のAPI呼び出しや正解の変更はしていない。丸めで説明できる回答と不正回答の回帰テストを追加した。これは接続上の誤拒否の修正であり、上記の意味的な精度を改善したという主張ではない。

## 採用判断と次の実装

私は、確認済み事実から限定した分類を行う補助としてのJev利用は継続するが、現在の2軸をそのまま利用者一般の総合適合度には使わないと判断する。明白な形状分類は仕様を構造化すればコードで済む。Jevを使うのは、コードで確定した状態が具体的な使い方に与える意味の判断へ絞る。

1. 未確認・矛盾を文字列の事実へ変換せず、取得元の確認状態でモデル呼び出し前に止める。既存の欠損キーによる停止を、仕様取得・利用条件の構造化に正しく接続する。
2. 利用者が不要とした軸をコードで外し、固定希望などの必須条件は機械判定する。候補の状態に合わせて重みを都合よく変えない。
3. 「折り畳み」「高W」「ポート多数」を普遍的な上位尺度にしない。質問は利用者の希望を満たすかという単一観点で作り直す。
4. 表示内容を「実際の印字」と「資料内の役割説明」に分けて構造化する。日本語自由文をそのままJevの事実解釈へ使う経路を見直す。
5. 同じ開発ケースで改善しただけで合格扱いせず、変更後に新しい独立ケースを私が事前判定して測る。実商品への一般化は、実商品仕様と根拠を用いた検証で別に判断する。

公式も信頼度を回答分布の性質として説明しており、正しさの保証とはしていない。[Confidence公式資料](https://docs.typesafe.ai/confidence)。今回の信頼度0.99の誤りは、その制限がこの用途でも実際に現れる証拠になった。
